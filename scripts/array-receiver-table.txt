# scripts/array-receiver-table.txt — the canonical row source for the
# ADR-0004 node-differential table.
#
# FORMAT (one directive per line, `#` starts a comment, blank lines ignored)
#
#   receiver <name>
#   decl     <expression that evaluates to the receiver>
#   method   <method-name> <call expression, in terms of `o`>
#
# Everything else about a row — the observation harness, the JSON of the
# generated Rust, the `expected` values — is DERIVED by
# scripts/gen-array-receiver-table.py. `expected` is whatever `node` printed
# for the generated program, so regenerating is a command, not a transcription.
#
# WHY THE RECEIVERS ARE NINE. ADR-0004's table was measured on ONE receiver
# (`{0:"a",1:"b",2:"c",length:3}`) and generalised from it to "17 of 24
# methods diverge". That is the claim this table exists to make checkable:
# every receiver below is a distinct rung of `LengthOfArrayLike` +
# `HasProperty`/`Get`/`Set`, and a method that is right on one is still wrong
# on another. `sparse_ctor` and `length_assigned` are deliberately redundant
# — `new Array(3)` and `[]; o.length = 3` reach the same declared length by
# different constructors, and Batch 2's `store_shape_extension` fix touched
# exactly that construction.
# The last four rows are NOT Array.prototype methods and they are the four
# most important rows in the file. They exist because Batch 1's table marked
# the sparse receivers as matching `node` while `new Array(3)` followed by
# `a[0] = "z"` reported `length` 1 where node reports 3 — and every row the
# table actually contained was a METHOD call, which either writes every index
# (`fill`, `copyWithin`) or goes through `set_array_len` (`push`, `pop`,
# `splice`), so nothing in it could ever observe a partial index write below a
# declared length. `ArraySetLength` is reachable only by writing one index.
# A table that cannot see the bug it is cited for is the same failure as a
# transcribed one, one level up.
